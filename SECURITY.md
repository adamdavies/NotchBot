# Security Policy

## Reporting A Vulnerability

Use GitHub's **Security > Report a vulnerability** private vulnerability reporting flow when it is available for this repository. If it is unavailable, open a GitHub issue containing no secrets, credentials, private payloads, or exploitable details and ask the maintainers to establish a private disclosure channel.

## Threat Model

NotchBot treats the current macOS user account as its trust boundary. Its Unix datagram sockets are mode `0600`, and lifecycle events and permission responses use independently authenticated encrypted envelopes with a key stored as mode `0600`. This excludes other local users and rejects accidental or unauthenticated messages, but it cannot isolate processes owned by the same user because they can potentially read the key. A compromised same-user process can inspect integration files, invoke the helper, forge lifecycle events, or submit permission responses. NotchBot does not attempt to isolate or secure OpenCode, Claude Code, terminals, or the projects they operate on.

NotchBot is local-only by design. It includes no telemetry or analytics and makes no intentional Internet requests. The integrated agents have separate network and data-handling behavior outside this threat model.

## Data Flow

The OpenCode plugin and Claude Code hooks invoke `~/Library/Application Support/NotchBot/bin/notchbot-hook`. The helper selects lifecycle state, source, session identifier, optional parent-session identifier, working-directory path, terminal identifier, reason, expiry, a bounded session title, a bounded current-activity description, and optional permission metadata. Current activity is selected only from Claude's native `description` field for Bash and agent tools and OpenCode's native tool-state title; OpenCode uses provider timestamps to reject delayed title and activity updates. When the user explicitly enables usage and cost tracking, the helper also accepts a numeric provider-reported estimated USD cost, an opaque OpenCode process generation identifier used for deduplication, and a single context-window percentage validated to be finite and within 0 to 100. The percentage is accepted only on metadata events from Claude Code or OpenCode; a preview or lifecycle event carrying one is rejected. A malformed or out-of-range provider percentage is treated as unavailable and clears an older reading, while the authenticated app-facing event validator rejects out-of-range values rather than clamping them. It authenticates and encrypts the event to `~/Library/Application Support/NotchBot/notchbot.sock` using the same-user key at `~/Library/Application Support/NotchBot/event.key`. Outside bounded native permission context and these narrow activity fields, NotchBot does not select prompt fields, transcripts, task subjects, task descriptions, tool commands or input/output, assistant response text, model details, or token details. Session titles and activity descriptions appear on separate hover-queue lines, remain in process memory, and are not used for notifications, permissions, cost attribution, or queue identity. NotchBot uses the working-directory path without traversing or reading arbitrary project files.

For an actionable permission, the helper binds a private one-shot `permission-<random-token>.sock` before publishing the event. NotchBot sends an authenticated `allowOnce`, `alwaysAllow`, or `decline` response to the socket derived from that validated token. Responses are single-use in practice because the helper closes and removes the socket after receiving one valid response; tokens and socket paths expire after a bounded four-minute wait. OpenCode retains its native request identifier inside the plugin and maps the response to `once`, `always`, or `reject`. Claude Code retains its native permission suggestion inside the helper. NotchBot offers Claude **Always** only when exactly one suggestion exists, and the helper echoes that suggestion without widening or synthesizing a rule. On timeout, app absence, invalid data, or provider API failure, the native provider permission flow remains available.

Permission rows separate the native permission scope from its command, path, URL, query, pattern, or description context when available. Both fields are sanitized, independently limited to 240 characters and 1 KiB, retained only in process memory, and never written by NotchBot. OpenCode context is selected from an allowlist of native permission metadata fields; Claude context is selected from the existing allowlisted `tool_input` fields. Unknown raw provider fields are not forwarded. Clicking an actionable row or the compact bot acknowledges the visual attention state and focuses the terminal without sending or hiding the unresolved request. Only an explicit permission button sends a provider response. After a response is sent, the controls disappear until the provider reports resolution.

Acknowledged attention entries remain in memory as Idle until a new request or lifecycle event needs attention, the session ends, or stale-session cleanup removes them. Unresolved request metadata and permission controls remain available after visual acknowledgement.

Daily coolness persists a local date identifier and aggregate observed top-level completion count in `UserDefaults`. Visual tiers, including Cap at 150 completions, are derived from that count and add no retained data. When usage and cost tracking is enabled, estimated daily spend persists the local date, aggregate estimated USD total, and up to 10,000 source-qualified cumulative cost baselines needed to deduplicate provider updates across app restarts and midnight; inactive baselines are pruned. The optional daily cost alert persists only the user-entered USD threshold and a day-scoped boolean recording that today's notification has been sent; both are cleared when usage and cost tracking is disabled, and neither leaves the machine. Context-window usage adds no persistence of any kind: percentages exist only in the running app's process memory, are removed with the session that reported them, and are cleared immediately when tracking is disabled. Debug previews do not modify persisted progress or spend.

The session timeline behind the Today view is the only NotchBot state that writes provider-supplied presentation text to disk, and it is a deliberate change to the retained-data story. When a session cycle reaches a terminal state, `session-timeline.json` records a stable cycle identifier, the source, the session identifier, an optional parent-session identifier, a group identifier, the same bounded and sanitized session title already shown in the hover queue, the cycle's start and end timestamps, and an optional estimated USD cost. It records nothing else: working directories, activity descriptions, permission scope and context, reasons, terminal identifiers and process IDs, context-window usage, prompts, transcripts, assistant responses, token counts, and model details are all excluded and are not written in any form. The file is written through the same no-follow, atomic-rename path as every other managed file, with mode `0600` inside the mode-`0700` support directory; a destination that is not a user-owned regular file is refused rather than followed or replaced. Reads are bounded, and an oversized, malformed, or unsupported-version document is discarded instead of trusted. Retention is the current local day only, bounded to 400 entries and 64 KiB, trimming the oldest complete parent/subagent groups first so a pathological day cannot grow the file without limit. An absent cost and a zero cost are distinct: zero means the cycle was tracked and cost nothing, and absent means no cost was observed, so cycles that completed while tracking was off carry no figure. Per-cycle cost is a delta from the cumulative baseline already persisted for the daily total, so it adds no new retained data and a session resumed after a restart is not charged for spend that predates it. Entries are written only on a provider-reported terminal state; clearing a row by hand, stale-session cleanup, capacity eviction, delayed-event rejection, and attention expiry all remove rows without recording anything. The file is deleted at the local-midnight rollover, when a document for an earlier day is found at startup, and as part of integration removal, and disabling usage and cost tracking strips costs from the rows already recorded. A persistence failure is non-fatal and never blocks live queue processing.

Claude Code passes its hook JSON on stdin. While usage and cost tracking is enabled, a generated status-line wrapper also passes Claude's documented status-line JSON to the helper and then invokes the complete prior status-line command with the original input. The decoder selects only the session ID, the numeric estimated cost, and the numeric context-window percentage Claude reports. Prompt, transcript, response, model, rate-limit, and token fields can reach the helper process in raw Claude input, but they are not selected, forwarded, or retained.

OpenCode constructs an allowlisted stdin payload and, only after opt-in, selects numeric assistant-message cost estimates; it does not pass through raw events or assistant-message content. Because OpenCode exposes no percentage of its own, the generated plugin derives one in process: it reads five numeric token counts from a completed assistant message and the model's numeric context limit from the documented `chat.params` hook, retains only that limit and the derived percentage in plugin process memory for the session, then divides, rounds, and bounds the result to 0 to 100. Only that scalar is written to the helper payload. Token counts, the context limit, and model or provider identifiers are never forwarded, logged, or persisted, and the hook returns its output unmodified so the plugin cannot influence the request. Compaction, message removal, and session deletion drop the stored value so a percentage that has stopped being true is retracted rather than displayed. The figure measures context used against the full context window and is not a prediction of the provider's automatic-compaction threshold.

The integration uses the helper and its `.notchbot-owner` marker, `integration-installation.json`, transactional `integration-backups/claude-settings-<UUID>.backup` files, `event.key`, `instance.lock`, `notchbot.sock`, `~/.config/opencode/plugins/notchbot.js`, and NotchBot handlers in `~/.claude/settings.json`. The Today view additionally uses `session-timeline.json`. Opt-in usage and cost tracking additionally uses the owned `bin/notchbot-statusline` wrapper and `statusline-state.json`, which stores the prior Claude status-line configuration for restoration. All relative names are under `~/Library/Application Support/NotchBot/`. Managed files are written through user-owned, no-follow directory descriptors to restrictive same-directory temporary files; final permissions are applied before atomic rename. Transactional settings backups use mode `0600`, are removed after a verified update, and are retained only on failure, with at most the five newest recognized backups kept. Unrecognized files, directories, and symlinks are not pruned, and backups are not restored automatically. Missing or invalid status-line recovery state prevents disabling usage and cost tracking from changing Claude settings, and uninstall validates managed-file ownership before changing settings. Uninstall also checks up front that the session timeline is a safely removable user-owned regular file and aborts the whole removal if it is not, then unlinks it last, without following symlinks and without recursive deletion, after every other ownership check has passed. These controls protect against accidental path substitution but do not isolate NotchBot from a malicious process running as the same user. NotchBot does not install integration files outside these paths.

## Sandbox Status

NotchBot 1.0.0 is not App Sandbox enabled and requests no signing entitlements.
